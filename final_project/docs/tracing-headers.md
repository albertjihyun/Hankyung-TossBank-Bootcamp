# 공통 헤더 규약 — X-Request-Id · traceparent (전 API 공통)

> 원본: 팀 노션 「공통 헤더 규약」(2026-07-30). API 명세서 DB가 엔드포인트 행 단위라 "모든 API 공통" 규약을 놓을 자리가 없어 별도 문서로 관리하던 것의 이관본. 관련 이슈: #141 · #134 · #151
>
> 배경: 오류 하나를 추적하려면 FE·Spring·FastAPI 세 시스템의 로그를 시간으로 눈대중해야 했다. 세 시스템이 같은 키를 주고받게 하는 규약이다.

## 1. X-Request-Id — 요청 하나를 세 시스템에서 잇는 키

| 항목 | 규칙 |
|---|---|
| 생성 | **최초 진입 서비스**가 만든다. FE가 만들면 FE 값이 끝까지 살아간다 |
| 형식 | `[A-Za-z0-9_-]{16,64}` |
| 수용 | 들어온 값이 형식에 맞으면 **그대로 유지**. 형식에 안 맞으면 **버리고 새로 만든다** |
| 전파 | 하위 호출에 그대로 실어 보낸다 (FE→Spring→FastAPI, FastAPI→Spring) |
| 응답 | **응답 헤더로 echo** — FE가 사용자에게 보여주거나 문의에 첨부할 수 있게 |

### 왜 형식 검증을 하나

들어온 값을 무조건 믿으면 **로그 주입**이 된다 — 개행·제어문자로 로그 한 줄을 여러 줄로 쪼개거나, 수백 KB 문자열로 로그를 부풀릴 수 있다. 그래서 화이트리스트 형식에 맞을 때만 유지하고, 아니면 조용히 새 값으로 교체한다. **400을 내지 않는다** — 추적 편의 기능이 요청을 막으면 안 된다.

### 담당별 역할

- **FE**: 요청마다 생성해 전송, 오류 화면에 노출 (문의 시 첨부)
- **Spring**: 수용·검증 → MDC 기록 → AI 호출 시 전달
- **FastAPI**: inbound 수용 → Spring 호출 시 전달, 응답 헤더 echo

규약 제정 시점(07-30) 실측: FastAPI는 inbound를 무시하고 매번 새로 만들고 있었고(`app/core/errors.py`), Spring 호출 헤더에 `X-Internal-Token` 하나만 실려 있었다 — 이 간극을 메우는 것이 규약의 목적. 스트림 내부 오류에도 실린다 — CH-2·S-4의 in-stream `error` 이벤트에 `requestId` 추가(07-28). 종전에는 스트림 시작 전 실패(HTTP 봉투)에만 있어, 정작 사용자가 신고하는 쪽을 추적할 수 없었다.

## 2. traceparent / tracestate — 분산 트레이싱

[W3C Trace Context](https://www.w3.org/TR/trace-context/) 표준을 쓴다. tracing이 켜졌을 때만 전파.

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
              │  └ trace-id (32 hex)            └ span-id (16)   └ flags
              └ version
```

- **X-Request-Id와 역할이 다르다** — X-Request-Id는 사람이 로그를 grep하는 키, traceparent는 APM 도구가 스팬 트리를 그리는 키. 둘 다 필요하며 하나로 합치지 않는다.
- 표준 헤더이므로 이름을 바꾸지 않는다 (`X-Trace-Id` 같은 자체 이름 금지) — OpenTelemetry SDK가 자동으로 읽고 쓴다.
- MVP 범위 밖 — 규약만 정해두고, 도입 시 각 서비스가 OTel 계측을 붙인다.

## 3. 요청이 흐르는 모양

```
FE                Spring                  FastAPI               Spring(internal)
│
├─ X-Request-Id: abc123…
│  ────────────▶ │
│                ├─ 형식 검증 → MDC 기록
│                ├─ X-Request-Id: abc123… (유지)
│                │  ──────────────────────▶ │
│                │                          ├─ inbound 수용(유지)
│                │                          ├─ X-Internal-Token
│                │                          ├─ X-Request-Id: abc123…
│                │                          │  ──────────────────────▶ │
│ ◀──────────────┴──────────────────────────┴──── 응답 헤더로 echo ──────┘
│  X-Request-Id: abc123…
```

**한 값이 끝까지 살아남는 것**이 목표다. 중간에서 새로 만들면 그 지점 앞뒤가 끊긴다.

## 4. 하지 않는 것

| 항목 | 이유 |
|---|---|
| X-Request-Id 형식 위반에 400 | 추적 편의 기능이 요청을 막으면 안 된다. 조용히 교체 |
| 응답 본문에 requestId 추가 (전 API) | 이미 오류 봉투(`error.requestId`)와 응답 헤더에 있다 |
| 자체 트레이스 헤더 신설 | W3C 표준을 쓴다 — 도구 생태계가 그걸 읽는다 |
| X-Request-Id를 인증·인가에 사용 | 클라이언트가 정하는 값이라 신뢰 근거가 될 수 없다. 신원은 JWT `sub`·`X-Internal-Token` |
