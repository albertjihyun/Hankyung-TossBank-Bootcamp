# 나비스(Narvis) 서비스 기획 개요

> 에이전틱 커머스 플랫폼 · Next.js + Spring Boot + FastAPI(LLM) · MVP 2026-07-16 → 고도화 2026-07-31
>
> 원본: 팀 노션 「자비스(JARVIS) 서비스 기획서」(2026-07-02 작성). 기획 당시 서비스명은 자비스였으며 2026-08-07 **나비스(Narvis)** 로 개명, `narvis.shop` 으로 배포되었다. 이 문서는 기획 시점의 계획을 보존하되, 최종 구현과 달라진 지점을 문서 끝의 [최종 구현과의 차이](#최종-구현과의-차이)에 정리했다.

## 0. 일정 및 마일스톤

- **~7/16 (MVP)**: 전 카테고리 상품이 존재하는 에이전틱 쇼핑몰의 핵심 플로우를 동작 수준까지 완성. 구매자 측 대화형 추천 + 장바구니, 판매자 측 최소 기능.
- **~7/31 (고도화)**: 개인화 추천 품질 개선, 판매자 대시보드/인사이트, 로그 분석 등 부가 기능 구체화.
- MVP 기준: "돌아가는가"가 아니라 "핵심 사용자 시나리오가 끊김 없이 완결되는가".

## 1. 서비스 개요

### 1-1. 한 줄 소개

**나비스(당시 자비스: "자"신만을 위한 쇼핑 "비"서 서비"스")** — 모든 카테고리의 상품을 갖춘 종합 쇼핑몰이되, 검색·필터가 아니라 **대화형 에이전트가 개인화된 추천으로 상품을 찾아가게 하는** 에이전틱 커머스 플랫폼.

### 1-2. 배경 및 문제 정의

- 종합 쇼핑몰은 카탈로그가 방대해질수록 "내가 뭘 사야 하는지" 자체를 사용자가 정의해야 하는 부담이 큼. 검색어를 정확히 알아야 하고, 필터를 일일이 조작해야 함.
- 상황은 있는데 상품명을 모르는 경우("여행 갈 건데 뭐 챙기지")를 기존 커머스 UX는 잘 못 다룸.
- 추천이 있어도 대개 비개인화(인기순·연관구매)라, 사용자의 맥락·취향이 누적·반영되지 않음.

→ 사용자가 **상황·의도를 자연어로 던지면**, 에이전트가 카탈로그 전체에서 개인화된 조합을 구성해 주는 경험을 제공하고자 함.

### 1-3. 타깃

특정 인구집단으로 한정하지 않음. 종합 커머스를 쓰는 일반 소비자 전반. (발표·데모 시나리오는 대표 유스케이스 1~2개를 선정해 시연.)

## 2. 서비스 컨셉과 차별점

- **넓은 카탈로그 + 좁혀주는 에이전트**: 카테고리 범위를 좁혀 차별화하지 않음. 카탈로그는 전 카테고리를 두되, **발견(discovery)을 에이전트가 대신**해 준다. 예: "여행 갈 건데 필요한 것 추천해줘" → 선크림 추천 3개 + 더보기 / 일회용품 추천 3개 + 더보기 식으로 카테고리를 가로질러 묶어 제시.
- **개인화가 핵심 차별점**: 이 쇼핑몰·에이전트를 사용한 맥락과 취향을 LLM 측 DB에 저장·업데이트하고, 그를 기반으로 지속적으로 개인화된 추천을 제공.
- **양면(구매자/판매자) 구조**: 구매자에게는 대화형 추천을, 판매자에게는 자사 상품 로그·데이터 기반 인사이트를 제공.

## 3. 페이지 구성

### 3-0. 기본

- 랜딩페이지: 서비스 소개 및 라우팅 유도 — MVP 이후 단계에서 진행
- 로그인/회원가입: 일반(이메일) 로그인/회원가입 (OAuth는 MVP 제외, 고도화 후보)
- 상품 상세페이지: 브랜드 홈·결제 페이지로의 이동 진입점
- 브랜드 홈: 추천 결과/상세페이지/챗봇에서 진입
- 장바구니, 결제 화면 등 쇼핑몰 기본 페이지

### 3-1. 메인 페이지

- 상단: 마이페이지 등 네비게이션 · 카테고리 해시태그
- 중앙: **취향 or 인기 상품** 영역 (로그인 시 취향 기반, 비로그인 시 인기 상품)
- 하단: **질문 입력창** — 에이전트에게 바로 질문하는 진입점

### 3-2. 검색(대화) 결과 페이지

- 좌측: **대화창** — 에이전트와의 대화 이력, 입력창 (디자인 시안 확정 07-07)
- 우측: **AI가 고른 결과** — 추출된 조건 칩(제거 가능) + 상품 카드 그리드
- 대화 세션 초기화: 로그아웃, 탭 종료, 일정 시간(5~10분) 경과, 새 대화 시작 시
- 쇼핑과 관련 없는 질문에도 채팅으로는 답변하되, 상품 영역은 인기/추천 상품을 유지
- 대화 중심 화면은 이 2개(메인 / 검색 결과)로 유지하고, 상세·브랜드 홈·장바구니·마이페이지 등은 표준 커머스 페이지로 구성

### 3-3. 마이페이지

- 주문 내역: 후기 작성 / 작성한 후기 조회 / 환불·반품 신청
- 취소/반품 내역
- 최근 본 상품 / 찜한 상품
- 프로필(취향), 배송지 관리
- 배송 조회는 MVP 이후

### 3-4. 판매자 페이지

- **대시보드 / 인사이트**: 자사 상품의 로그·판매 데이터를 분석해 요약 정보 제공. 판매자가 자연어로 질문("오늘 왜 매출 떨어졌어?")하면 로그 기반으로 답변.
- **AI 상세페이지 편집 보조**: 판매자가 AI에게 상세페이지 개선을 요청. AI는 직접 반영이 아니라 제안하고 최종 판단은 판매자가.

> 기능 범위 메모: 판매자 기능은 고도화(7/31) 구간의 핵심. MVP(7/16)에서는 구매자 플로우 완성을 우선하고, 판매자 페이지는 최소 동작(로그 조회 수준)만.

### 3-5. 로그 단

- 서비스 전체의 퍼널 로그(상세페이지만 본 경우 / 장바구니까지 / 결제까지), 카테고리별 판매 특성 수집.
- 퍼널·판매 로그 수집은 별도 UI 없이 로그 단에서 처리하며, 이 데이터가 3-4 판매자 인사이트의 소스.

## 4. 주요 기능

### 4-1. 상품 추천 (핵심)

- 상황별로 케이스를 분기해 처리:
  - **Case 1**: 상품명만 입력 → 추천 task LLM
  - **Case 2**: 필터링(옵션이 들어간 상품명)
  - **Case 3**: 상황 기반 질문 (예: "여행 갈 건데 필요한 거 추천해줘" → 카테고리를 가로질러 선크림·일회용품 등을 묶음)
- 추천 시 고려사항: 예산 / 카테고리 / 상황 / 취향 / 사용자 과거 데이터 → 상품 스펙으로 연결
- **개인화**: LLM 측 DB에 누적된 맥락·취향을 반영해 같은 질문이라도 사용자별로 다른 결과를 제시 (핵심 차별점이자 데모 포인트)
- 핵심 사용 시나리오: (1) 추천 → (2) "내가 살 테니 담아줘" 자연어 담기

### 4-2. 결제 자동화

- DB 조작·조회 기반. **장바구니 담기까지만** 자동화 (실결제는 사용자가 직접).

### 4-3. 로그 분석 (판매자용)

- 매출 이상 탐지 → 매출 급감 여부 → 원인 분석
- 고객 행동 분석, 이탈 원인 분석 (퍼널 상 어느 지점에서 멈추는지)
- 판매자 질문(예: "오늘 왜 매출 떨어졌어?") → 판매자용 인사이트 제공
- 데이터: 자체 로그에서 확보, 초기엔 더미데이터 활용

> 강사 피드백: 보안·로그·재고관리는 이미 흔한 기능. 차별화 포인트는 "장바구니→결제 이탈 원인을 데이터로 분석"하는 지점에 두라는 제안.

## 5. 에이전트 사용처

| 기능 | 에이전트 역할 |
|---|---|
| 상품 추천 | 케이스 분기(상품명/필터/상황) 후 추천 |
| 프로필 구축 | 대화·구매 이력에서 사용자 프로필(예산·취향 등)을 누적 |
| 장바구니 담기 | 자연어 명령("담아줘")을 DB 조작으로 변환 — 장바구니까지만 |
| 판매자 인사이트 | 판매자의 자연어 질문에 로그 기반 분석으로 답변 |
| 상세페이지 편집 보조 | 판매자에게 가격·문구 개선을 제안 (직접 반영 없이 제안만) |

## 6. 범위 정의 (기획 시점)

### 포함 (MVP, ~7/16)

- 메인/검색 결과 2개 화면 중심의 종합 쇼핑몰 + 대화형 에이전트
- 상품 추천(케이스 분기) + 개인화(맥락·취향 누적/반영)
- 장바구니 자동화(담기까지), 기본 쇼핑몰 플로우
- 마이페이지 (주문 내역·후기·취소/반품·최근 본 상품·찜·배송지)
- 판매자 페이지는 최소 동작만
- 대표 데모 시나리오 1~2개를 끝까지 완성해 발표 방어력 확보

### 고도화 (~7/31)

- 개인화 추천 품질 개선
- 판매자 대시보드/인사이트, AI 상세페이지 편집 보조
- 로그 분석 고도화

### 보류

- 상품 등록 자동화/도우미 (상세페이지 자동 생성 등)
- 관리자 분석 확장 (마우스 히트맵 등)

### 제외 (기획 단계에서 결정)

- **자취생 타겟팅 전면 제외** — 특정 인구집단 한정에서 전 카테고리 종합 커머스로 전환
- **공구·나눔** — 자취생 캐릭터 기반 기능이라 함께 제외
- **자취 팁/레시피 콘텐츠** — 자취생 타겟과 묶여 제외
- **3D 방 배치** — Three.js 테스트는 성공했으나 모델링 부담·작업량 과다
- **판매자 입점 기능** — 입점 플로우는 빼고, 판매자 기능은 대시보드·편집 보조로 한정

## 최종 구현과의 차이

기획서 작성(07-02) 이후 실제 구현 과정에서 바뀐 사항. 최종 상태의 정본은 각 저장소의 코드와 API 명세(`jarvis-backend/docs/backend/04-api-spec.md`)다.

| 기획서 내용 | 최종 구현 |
|---|---|
| 서비스명 자비스(JARVIS) | **나비스(Narvis)** 로 개명 (2026-08-07), `narvis.shop` 배포 |
| 비회원은 초기 3회만 사용 가능 | **폐기** (07-07 결정) — 게스트도 무제한 채팅 가능, 개인화만 미적용. 게스트 쿼터 API(CH-4)도 폐기 |
| CS 자동화 / 문의 챗봇 (4-3절의 문의·환불 응대) | **폐기** — 문의 챗봇(CH-3), 문의 접수(I-5), 문의 내역(M-9) 전부 미구현. AI는 추천·장바구니·판매자 분석에 집중 |
| 관리자 페이지 (문의·신고·클레임 처리) | **미구현** — 관리자 API(AD-1~7) 전부 폐기. 후기 신고 접수(M-3)만 존재하고 처리 기능은 없음 |
| 판매자 상세페이지 직접 수정 | 직접 수정 API(S-5) **폐기** — 판매자 에이전트 챗을 통한 **HITL 드래프트 방식**(AI가 초안 제안 → 판매자 확정)으로 대체 |
| 환불·반품·교환 | **교환 제거** (07-17 확정) — 취소·반품만 지원 |
| 배송 조회 (MVP 이후) | 최종까지 미구현 |
| OAuth 소셜 로그인 (고도화 후보) | 최종까지 미구현 (이메일 로그인만) |
