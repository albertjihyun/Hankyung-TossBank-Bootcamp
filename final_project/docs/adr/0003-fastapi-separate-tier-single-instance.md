# ADR-0003: FastAPI는 별도 티어로 분리하되 의도적으로 1대만 둔다

- 결정일: 2026-07-09 (분리 결정 후 같은 날 "1대 고정"으로 수정)
- 상태: 채택
- 근거 문서: `jarvis-backend/docs/backend/03-architecture.md` D-분산8

## 맥락

분산 형상에서 next·spring은 무상태라 복제한다. FastAPI(LLM 서버)를 어디에 둘지: 앱 서버에 동거시킬지, 분리한다면 몇 대로 복제할지.

## 결정

**별도 티어로 분리하되 복제하지 않고 정확히 1대**만 둔다.

## 근거와 기각된 대안

**왜 별도 티어인가** — 스케일 신호(사용자 트래픽 vs LLM 대기), 소유 팀, 자원 형상(임베딩·메모리), 장애 격리가 모두 앱 서버와 다르다.

**왜 1대인가 (복제 기각)**

1. **죽어도 되는 유일한 계층** — FastAPI 실패는 `LLM_UNAVAILABLE`로 degrade되고 쇼핑몰은 정상 동작한다(채팅만 잠깐 불가). SPOF여도 괜찮은 유일한 곳.
2. **부하 병목이 아니다** — 채팅의 시간은 외부 LLM API 대기(I/O)라 1대가 동시 연결 다수를 감당한다.
3. **대화 맥락이 인메모리다** — 1대면 모든 턴이 같은 인스턴스로 가서 맥락이 유지된다. 복제하면 맥락이 갈라져 외부화 또는 sticky 세션이 필요해진다 — 늘리지 않음으로써 그 비용 자체를 회피한다. (Redis에는 세션 ID·TTL만, 맥락은 FastAPI 메모리.)

## 트레이드오프·결과

- 단일 인스턴스이므로 배포 파이프라인에서 **자동 복구가 필수** 요건이 됐다 (`jarvis-ai/.github/workflows/deploy.yml`의 명시 주석).
- SSE 직결 전환([ADR-0005](0005-sse-direct-connect.md)) 이후 FastAPI는 인터넷에 공개되지만, 공개 포트는 SSE 읽기뿐이고 `/internal` 콜백은 여전히 spring 티어에서 온 것만 받는다.
