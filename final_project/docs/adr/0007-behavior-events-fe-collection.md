# ADR-0007: user_event 폐기 — 행동 이벤트는 FE가 수집한다

- 결정일: 2026-07-17 (로그·분석 팀 합의)
- 상태: 채택 (구현 시작 전 전면 재설계 — 전환 비용 0)
- 근거 문서: `jarvis-backend/docs/backend/02-data-model.md` D31·D32·D35, `03-architecture.md` D6(폐기)

## 맥락

원래 설계는 서버 측 `user_event` 테이블 + `@Async`/`AFTER_COMMIT` 이벤트 발행이었다. 그러나 판매자 분석에 필요한 `page_view`·`session_start`·`search` 같은 이벤트는 **서버가 구조적으로 알 수 없다** — 페이지를 본 것은 브라우저에서 일어나는 일이다.

## 결정

행동 로깅 전체를 **FE SDK가 배치 수집해 `POST /api/events`(E-1)로 전송**하는 구조로 바꾼다. 서버 측 `user_event`와 `@Async` 발행(D6)은 폐기. 안전장치:

- **8종 타입 화이트리스트** — 미지 타입은 경고 로그 후 폐기
- **신원은 서버가 주입** — member_id는 JWT에서, guest_id는 쿠키에서. body의 신원 주장은 무시
- **멱등성은 DB가 강제** — FE가 이벤트마다 UUID(`client_event_id`)를 발급, UNIQUE 제약이 네트워크 재시도 중복의 최종 방어선. `INSERT IGNORE`로 뭉개지 말 것(타입 오류 같은 비중복 에러까지 삼킨다)이 명시됨

서버만 아는 사실(주문 상태 전이·상품 변경·계정 이벤트)은 별도의 **append-only 로그 테이블 3종**에, 상태 변경과 **같은 트랜잭션**으로 기록한다. 주문 전이는 단일 서비스(`OrderStatusChanger`)로만 지나가게 해 "로그 누락을 코드 리뷰가 아니라 구조로 차단"한다 (D32 — "히스토리 테이블은 YAGNI"였던 01 D6을 소비자(분석 에이전트) 등장으로 번복).

## 기각된 대안

- **user_event 확장 + 서버 발행 유지**: page_view류를 서버가 알 수 없어 불가.
- **양쪽 병행**: 같은 퍼널이 두 테이블에 갈라져 모든 분석이 2소스 조인이 되고 타입 정의가 중복된다.

## 트레이드오프·결과

- FE 발화는 이탈·차단기로 유실될 수 있다 — 분석은 추세로 읽고, 매출·정산의 진실은 `order_item`이 유지.
- 수집 위치 원칙은 이후에도 시험대에 올랐다: `add_to_cart`는 FE 수집이었다가 2026-08-06 "데이터가 실제로 바뀌는 지점(CartService)에서 기록"으로 BE 이관됐고, FE 제거와 BE 수집의 **배포 순서가 어긋나 유실 사고**가 났다 (`jarvis-frontend/docs/cart-event-migration-incident.md`) — 브랜치 분리가 배포 순서를 강제하지 않는다는 교훈.
