# ADR-0012: Kafka는 후보 7개 중 1개에만 — 기각의 기록

- 결정일: 2026-08-09~10 (운영 형상은 08-10, 토픽 네이밍 08-12)
- 상태: 채택 (S-1 activeVisitors 단독)
- 근거 문서: `jarvis-backend/docs/backend/08-kafka-design.md` §2, D6~D10

## 맥락

행동 이벤트 파이프라인에 Kafka 도입을 검토했다. 도입 자체보다 **어디에 쓰지 않을지**를 가리는 것이 본 작업이었다.

## 결정

4문항 적합성 테스트(서로 다른 동기의 소비자로 팬아웃되는가 / 명세에 실시간 요구가 있는가 / 소급 정정 없는 현재 시점 값인가 / 팀 간 계약 변경이 없는가)를 후보 7개에 적용, **S-1 실시간 방문자 수(activeVisitors)만 전부 통과**했다. 효과: 최대 테이블에 대한 30분 주기 스캔(결제와 같은 RDS에서)이 ZCARD 1회로 대체된다.

**기각 6건과 사유** (이쪽이 본체):

| 후보 | 기각 사유 |
|---|---|
| I-17 카탈로그 동기화 | 교과서적 CDC지만 소비자가 하나뿐이고 AI 팀 계약 변경이 필요 |
| 주문 이벤트 발행 | 하류 소비자가 존재하지 않는다 — "Kafka를 위해 기능을 발명하는 것" |
| 매출·주문 지표 | 돈은 근사할 수 없다 |
| S-1 aiAttribution | 취소의 소급 반영·정책 재평가가 필요한데 스트림 물질화는 그걸 불가능하게 한다 |
| 캐시 무효화 | 기존 커밋 후 evict로 충분 |
| 실시간 판매자 분석 | 실요구 없음 |

지적 정직성 항목 2건이 문서에 명기됨: "명세에 실시간이라 적혀 있다"는 **정당화로 쓰지 않는다**(명세를 우리가 썼으므로 순환 논증 — Kafka 검토보다 3주 앞선 요구였다는 증거로만 사용). 그리고 **30초 캐시로도 된다는 것을 인정** — 정확한 주장은 "캐시는 빈도를 줄이고, 스트림 집계는 작업 자체를 없앤다. Kafka를 써야 한다면 여기가 가장 방어 가능한 자리"까지다.

## 운영 형상

- **D6**: KRaft 단일 브로커, 복제 없음, 전용 EC2(사설 IP만, 보안그룹은 IP가 아니라 **참조**로 걸어 앱 스케일아웃 자동 커버), 보존 7일. 손실 상한은 DB 폴백 + `client_event_id` 멱등성이 잡아준다. 3브로커·RF3는 프로덕션 표준으로 명기.
- **D7** (배포 리뷰 후 전면 재작성): produce 실패 시 **동기 DB insert 폴백** 후 202 유지. 초안은 fail-fast 500(계약 순수성·관측성)이었으나 3가지 이유로 번복 — 현 단일 타깃그룹 ALB에서 경로별 5xx 알림 불가, 데모 중 브로커 장애가 콘솔 에러·SDK 재시도 폭풍으로 표출, 이미 폴백을 가진 D5와 비일관. 제약: **조용한 드랍으로는 퇴행 금지**.
- **D9**: 컨슈머는 별도 배포 단위가 아니라 **Spring 앱 내 `@KafkaListener`**. "병목에서 일을 뗐다"는 주장의 범위를 정확히 고정 — 뗀 것은 RDS 스캔과 S-1 집계이지 앱 계층 수집이 아니다(그건 이미 4대가 `@Async`로 하고 있고 트리거만 바뀜). 기각: 브로커 EC2에 컨슈머 동거(운명 공유로 장애 대책 무의미화), 별도 레포(코드 중복).
- **D10**: dev·prod가 같은 브로커를 쓰므로 토픽·그룹명에 환경 프리픽스.
