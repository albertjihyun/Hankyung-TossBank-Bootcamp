# ADR-0002: LLM 서버는 DB에 직접 접근하지 않는다 — 읽기 전용도

- 결정일: 2026-07-09 (팀 합의)
- 상태: 채택 (전 기간 유지. 벡터 저장소는 명시적 예외 — 본문 참조)
- 근거 문서: `jarvis-backend/docs/backend/03-architecture.md` D7, `05-llm-contract.md` §0-1

## 맥락

FastAPI(LLM 서버)가 추천 후보 검색·주문 상태 조회 등을 위해 커머스 데이터를 읽어야 한다. "쓰기는 위험하니 막되, 읽기 전용 계정과 뷰로 좁혀 DB 직접 조회를 허용하자"(대안 B)는 안이 논의됐다 — LLM 팀의 개발 속도가 확실히 빨라지기 때문.

## 결정

**LLM의 모든 데이터 접근은 Spring의 `/internal/*` 콜백으로만** 한다. 읽기 전용 DB 접근도 허용하지 않는다.

## 근거와 기각된 대안

- **소유 데이터(주문·판매자 지표·PII)에서 읽기 전용 DB 접근은 아키텍처 모순이다.** 행 단위 스코핑을 하려면 DB가 FastAPI의 신원 주장을 믿어야 하는데, 이는 "신뢰의 근원은 JWT이고 FastAPI는 검증된 값의 메아리일 뿐"이라는 원칙을 뒤집는다.
- 소유 데이터는 **읽는 것 자체가 피해**다 — "쓰기 금지"는 방어가 되지 않는다.
- 공개 카탈로그 데이터에 한해 "과잉 방어"라는 비판은 타당하다고 인정하되, 대안 B가 이기는 유일한 축은 LLM 팀 속도이고, 그것은 A안의 개선(더 굵고 유연한 엔드포인트, 캐싱, 병렬 툴 호출)으로 회복 가능하다. 반면 B는 감사해야 할 접근 경로 이원화, text2SQL 오류, DB 부하 공유라는 영구 비용을 남긴다.
- 동반 원칙: 경계 통제는 인젝션의 **피해 반경**을 가두는 것이지 **성공 확률**을 낮추는 게 아니다 — 가드레일(LLM 팀)과 `/internal` 입력 전건 재검증(BE)은 서로를 면제하지 않는다.

## 예외

임베딩 벡터 저장소(pgvector)는 상태이므로 외부화하되 **FastAPI가 소유·직접 접근**한다 (D-분산9, 2026-07-16). 공개 카탈로그 + AI 생성 산출물만 담기 때문에 허용된 명시적 예외다. 구조화된 진실(가격·재고·상태)은 계속 Spring/MariaDB.

## 트레이드오프·결과

- 왕복 비용: 에이전트 요청은 유저 1왕복 대비 2왕복 중첩 구조가 된다.
- `/internal` 표면이 커지는 비용을 감수 (최종 29개 엔드포인트) — "벽을 트는 대신 창구를 넓힌다".
- AI 측에는 소스 컬럼 미러 금지 + AI 주도 pull 배치(I-17)로 정합 (`jarvis-ai/docs/api-spec.md` v0.5.x).
