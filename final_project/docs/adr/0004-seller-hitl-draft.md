# ADR-0004: 판매자 에이전트의 쓰기는 드래프트 + 사람 승인(HITL)으로만

- 결정일: 2026-07-13 (최초), 2026-07-17 (권한 모델의 예외로 공식화)
- 상태: 채택
- 근거 문서: `jarvis-backend/docs/backend/05-llm-contract.md` §0-1; `jarvis-ai` 판매자 에이전트 (`app/agents/seller/hitl.py`, `draft_lifecycle.py`)

## 맥락

판매자 챗봇이 "가격을 5% 내려줘" 같은 요청으로 상품 정보를 **수정**해야 한다. 그러나 권한 모델의 원칙은 "서비스 토큰 뒤에 위험한 능력을 두지 않는다"이고, 상품 수정은 매출에 직결되는 쓰기다. 기획 단계의 "판매자 상품 직접 수정 API(S-5)"는 이 원칙과 충돌해 폐기됐다.

## 결정

판매자 에이전트의 모든 쓰기는 **드래프트 제안 → 판매자 명시 승인 → 실행**의 2단계로만 진행한다. 챗봇은 SSE `draft` 이벤트로 변경 diff 카드를 제안하고, 판매자가 승인해야 별도 확정 액션으로 실행된다.

이것은 "위험 능력을 서비스 토큰 뒤에 두지 않는다" 규칙의 **유일한 승인된 예외**로 기록됐다. 판매자의 승인이 "본인 JWT로 직접 실행"을 대체하는 것으로 간주하되, 보상 통제를 함께 건다:

- **draftId 바인딩** — 화면에 보여준 것과 실행되는 것이 동일함을 보장
- **brandId 경로 하드게이트** — 티켓 클레임에서 유도하고 Spring이 재검증 (판매자가 주장할 수 없음)
- **대기 TTL** — 승인 대기 드래프트는 시간 제한 후 소멸

## 기각된 대안

- 판매자 상품 직접 수정 API(S-5): 원칙 충돌로 폐기. 수정 경로를 에이전트 HITL로 단일화.
- 에이전트 자동 반영(승인 생략): 기획 단계부터 배제 — "AI는 직접 반영이 아니라 제안, 최종 판단은 판매자".

## 경계

이 예외는 **판매자 자신의 브랜드 상품**으로 한정되며, 세 위험 축(금전·비가역, 제3자 영향, 권한 변경)으로는 확장 금지가 명문화됐다. 구매자 측 에이전트의 상한은 여전히 "장바구니 담기까지"다.

## 트레이드오프·결과

- 대화 흐름이 한 단계 길어지는 UX 비용을 감수하는 대신, "AI가 꼬임(인젝션)당해도 위험한 문이 없다"는 방어 구조를 유지.
- 발송 처리(I-30 주문 아이템 상태 전이), 상품 삭제(I-12 soft delete)도 같은 HITL 패턴을 재사용.
