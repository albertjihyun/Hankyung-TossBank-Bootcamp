## 1. 핵심 설계 철학 (우리가 중요하게 여긴 것 — README/LinkedIn 핵심)

이번 프로젝트의 한 줄: **"단순히 배포가 아니라, 대규모 서비스의 가용성을 처음부터 설계해본다."**
모든 결정은 아래 원칙에서 나왔다.

1. **상태를 어디 두느냐가 확장성을 정한다.** 상태(세션·카운터)를 앱 서버 메모리에 두면 인스턴스를 늘릴 수 없다. 상태를 공유 계층(DB/캐시)으로 빼내 앱을 **무상태**로 만들면, 그 순간 다중화·자동복구·오토스케일이 전부 열린다.
2. **정합성은 단일 집중(single source of truth)인 공유 DB에 둔다.** 동시성 제어도 **DB 레벨**(비관적 락 등)에서. JVM 락은 인스턴스가 여러 대면 무력하므로.
3. **체인은 가장 약한 고리만큼만 강하다.** 가용성은 SPOF가 결정한다. SPOF를 계층별(LB→앱→DB)로 하나씩 제거하는 것이 HA의 전부다.
4. **다중화 = 상태 확장 + 가용성의 양면.** 서버를 늘리면 용량도, 장애 내성도 같이 는다.
5. **앱 서버는 가축(cattle), 상태는 보배.** 앱 인스턴스는 언제든 죽고 새로 태어나도 되는 교체 가능한 존재여야 한다.
6. **"관리는 한 곳, 운명은 따로."** 같은 계정 안이라도 존/리전(독립 실패 영역)에 분산해 물리적 운명을 분리한다.
7. **위임할 것은 위임한다.** DB HA(복제·페일오버·스플릿브레인 방지)는 직접 만들지 말고 매니지드에 맡긴다.

## 2. 목표 아키텍처 (이상향 — "이런 방향이어야 한다")

```
[사용자]
   │  HTTPS  (TLS 종단: Cloudflare 또는 LB 관리형 인증서)
   ▼
[로드밸런서]  HA, 헬스체크 통과한 인스턴스로만 라우팅
   │
   ▼
[무상태 앱 인스턴스 그룹]  멀티존 분산 · 오토힐 · 오토스케일 · 커스텀 이미지(빠른 부팅)
   ├── 세션 ───────────────── [Redis]        (외부 세션 스토어 = 앱 무상태)
   └── 데이터 ─────────────── [매니지드 HA DB]  프라이머리 + 다른 존 standby, 자동 페일오버
                                  └────────── [읽기 레플리카]  (읽기 분산)

[Secret Manager] DB 비번·키        [비공개 버킷] 배포 산출물(jar)
[Monitoring / Logging + 알림]      [롤링 업데이트] 무중단 배포
```

계층별 목표 상태:
- **요구:** TLS 필수, LB는 관리형(자체 HA), 헬스체크 게이팅.
- **앱:** 무상태, 멀티존, 오토힐+오토스케일, **커스텀 이미지로 콜드스타트 최소화**.
- **세션:** Redis (DB 부하 분리, 빠름).
- **DB:** 매니지드 HA(프라이머리+standby+자동 페일오버) + 읽기 레플리카. 쓰기는 단일 프라이머리.
- **동시성(핫 카운터):** 가벼운 **원자적 조건부 UPDATE**(`UPDATE ... SET reserved=reserved+1 WHERE reserved<capacity`) 또는 Redis 원자연산. 락 보유 시간 최소화로 처리량 확보.
- **보안:** 비밀은 Secret Manager, 산출물은 비공개 버킷 + 서비스 계정 인증.
- **운영:** 지표·로그·알림(관측), 롤링 업데이트(무중단 배포).
- **멀티리전:** 글로벌 사용자/재해복구가 진짜 필요할 때만. 쓰기는 단일 프라이머리 리전, 타 리전은 읽기 레플리카. (멀티마스터는 강한 일관성과 상충 → 선착순에 부적합)

## 3. 이번 해커톤 구현 범위 (제약 기반 — Now vs Later) ★핵심

| 계층 | 이번 (제약 하에서) | 나중 (이상향) | 제약 / 이유 |
|------|--------------------|----------------|-------------|
| TLS | Cloudflare SSL(또는 LB 관리형 인증서) | 동일 유지 | 필수 → 반드시 적용 |
| LB | 매니지드 LB(헬스체크 게이팅). 단일 리전이면 **Regional LB** | 트래픽 따라 정책 고도화 | 단일 리전엔 Global LB 과함 |
| 앱 다중화 | MIG 멀티존 2대 + 오토힐 | + 오토스케일 정책 | 8h 내 오토스케일 튜닝까진 무리 |
| 콜드스타트 | 스타트업 스크립트(느림 감수) | **커스텀 이미지**로 단축 | 이미지 굽기 시간 부족 → 다음에 |
| 세션 | **Spring Session JDBC (MariaDB)** | **Redis** 세션 스토어 | 스택 제약상 Redis 불가 → DB에 안전 수용 |
| DB HA | 단일 MariaDB VM **+ 자동 백업** | **Cloud SQL HA + 읽기 레플리카** | 스택/시간 제약. 단일 DB는 알려진 약점 |
| 동시성 | **비관적 락(SELECT FOR UPDATE)** | + 원자적 조건부 UPDATE / Redis 카운터 | 비관적 락이 명확·정확(데모·면접용). 처리량 개선은 다음 |
| 비밀관리 | Secret Manager(권장) / 최소 환경변수 | Secret Manager 정착 | 메타데이터 평문 금지 |
| 산출물(jar) | 비공개 버킷 + 서비스 계정 | 동일 | 공개 버킷 금지 |
| 관측 | Actuator + 기본 로그 | Monitoring/Logging + 알림 대시보드 | 시간 제약, 기본만 |
| 배포 | 인스턴스 재생성 | **롤링 업데이트(무중단)** | 무중단 실측 시간 부족 |
| 리전 | 단일 리전 멀티존 | 필요 시 멀티리전(읽기 레플리카) | 멀티리전의 일관성/지연 트레이드오프 → 지금 불필요 |

> 읽는 법: **왼쪽이 이번 제출물, 오른쪽이 "제약이 풀리면 이렇게 간다"**. 제약 컬럼이 곧 README 트러블슈팅/설계 의사결정 근거가 된다.

## 4. 핵심 의사결정 근거 (의사결정 기록 — README/면접/LinkedIn용)

- **왜 DB 락인가?** 인스턴스가 여러 대면 `synchronized` 같은 JVM 락은 각 JVM에 갇혀 무력하다. 정합성의 단일 집중이 공유 DB에 있으니, 잠금도 DB에서 잡아야 인스턴스 수와 무관하게 직렬화된다.
- **왜 세션을 외부화하나?** 앱을 무상태로 만들어야 어느 인스턴스로 요청이 가도 로그인이 유지되고, 인스턴스를 자유롭게 늘리고 죽일 수 있다. 이번엔 제약상 MariaDB(Session JDBC), 이상적으론 Redis.
- **단일 DB가 약점인 걸 알면서 왜 이번에 감수하나?** 스택·시간 제약. 그리고 학습 우선순위가 "앱 계층 HA를 직접 설계·구현"이었기 때문. 약점의 위치를 *정확히 인지*하고 다음 단계(Cloud SQL HA)를 설계해둔 것이 핵심.
- **왜 멀티존이고 멀티리전이 아닌가?** 멀티리전은 DB 간 광역 복제 문제(동기=지연 폭증 / 비동기=유실·충돌)를 부르고, 비관적 락 기반 강한 일관성과 상충한다. 선착순처럼 강한 일관성이 필수인 서비스엔 "단일 리전 멀티존 + HA DB"가 스윗스팟.
- **왜 커스텀 이미지가 이 서비스에 중요한가?** 오픈런은 *오픈 그 순간* 트래픽이 폭발한다. 부팅에 시간이 다 걸리면 오토스케일이 폭주가 끝난 뒤 도착해 무용지물. 미리 구운 이미지로 부팅을 수초로 줄여야 스케일이 제때 붙는다.
- **왜 인스턴스가 매번 새로 생성되나(가축)?** MIG는 고정 VM 한 대를 재부팅하는 게 아니라, 필요 수만큼 템플릿으로 *새 VM*을 찍어낸다. 그래서 부팅 스크립트가 매번 멱등이어야 한다. 이것이 "가축" 패턴의 실제 동작이며, 그래서 부팅을 이미지에 미리 담는다.

## 5. 학습 요약 (LinkedIn 글감 — 한 문단 스토리)

> "8시간 해커톤에서 '동작하는 앱'을 넘어 **대규모 서비스의 가용성**을 처음부터 설계해봤다. 출발점은 단 한 가지 원칙 — *상태를 어디 두느냐가 확장성을 정한다*. 세션과 카운터를 앱 메모리에서 떼어 공유 계층으로 빼내 앱을 무상태로 만들자, 비로소 인스턴스를 여러 존에 분산하고 자동 복구시키는 다중화가 가능해졌다. 동시성은 JVM이 아니라 DB 레벨 락으로 잡아, 인스턴스가 몇 개든 선착순 정합성이 깨지지 않게 했다. 그리고 *체인은 가장 약한 고리만큼만 강하다*는 사실을 직접 확인했다 — 앱 계층을 HA로 만들어도 단일 DB가 남는 한 시스템 가용성은 거기에 묶인다. 실무 제약상 이번엔 세션을 DB에, DB를 단일 VM에 두었지만, 다음 단계(Redis 세션, Cloud SQL HA, 커스텀 이미지, 롤링 배포)를 설계로 남겨 약점의 위치와 해법을 명확히 했다. 가용성은 '안 죽게 만드는 것'이 아니라 *다 죽는 시나리오를 더 드문 사건으로 밀어 올리는 것*이라는 걸 배웠다."
