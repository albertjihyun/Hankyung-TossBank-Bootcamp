# 01. 주문 상태 머신 명세

> 기준 문서: 노션 「기능 정의 - 이소희」 (2026-07-07 확정본)
> 이 문서만 읽고 주문/클레임/후기 로직을 구현·검토할 수 있어야 한다. 모호한 지점이 나오면 이 문서를 고치고 나서 코드를 고친다.

## 0. 이 문서가 커버하는 요구사항

기능 정의에서 상태 머신이 필요한 지점:

- 결제 화면: 모의 결제, **결제 실패(모의 실패 케이스 포함) 시 안내 및 재시도**
- 마이페이지 주문 내역: **주문 건별 배송 상태 값 표시**, 후기 작성(**배송완료 상태의 주문 상품만**), 환불/반품/교환 신청
- 마이페이지 취소·반품·교환 내역: **신청 건 목록 및 처리 상태 조회**
- 문의 챗봇: "내 주문 어떻게 됐어?" → **주문 상태 값 기반 답변** (상태 문자열이 곧 LLM 콜백 응답)
- 관리자 페이지: **클레임(취소/반품/교환) 승인/거절 처리** (2026-07-07 팀 결정 — 기능 정의 11번에 반영됨)

---

## 1. 결정 로그

### D1. 상태를 주문(Order) 단위와 주문상품(OrderItem) 단위로 분리한다

- **문제**: 한 번의 주문에 여러 상품이 담긴다(장바구니 선택 주문이 기본 플로우). "반품 신청"이 주문 전체에 걸리는지 상품별인지 정해야 모델이 잡힌다.
- **선택지**:
  - (A) 주문 단위 상태 하나 — 단순하지만, 상품 2개 중 1개만 반품하는 순간 표현 불가
  - (B) 상품(아이템) 단위 상태만 — 표현력은 되지만 "결제 완료" 같은 주문 전체 개념이 아이템에 중복 저장됨
  - (C) 결제는 주문 단위, 이행(배송)/클레임은 아이템 단위로 분리
- **기준**: 기능 정의가 요구하는 최소 표현력. "후기는 배송완료 상태의 주문 **상품**만"이라는 문구 자체가 아이템 단위 상태를 전제한다. 반면 결제는 항상 주문 전체에 한 번 일어난다.
- **선택**: (C). 결제 상태는 `Order.status`, 배송·클레임 상태는 `OrderItem.status`.
- **트레이드오프**: 조회 시 조인 필요, "주문 대표 상태" 표시 규칙이 따로 필요(§4). 대신 부분 클레임이 자연스럽게 표현되고 ERD가 실무 표준과 같아져 학습 가치도 있음.

### D2. 클레임(취소/반품/교환)은 아이템 단위 · 전체 수량으로 한정한다

- **문제**: "키보드 2개 중 1개만 반품" 같은 부분 수량 클레임을 지원할지.
- **선택지**: (A) 수량 단위 클레임 (B) 아이템 단위(해당 아이템 전 수량) 클레임
- **기준**: 데모에서 보여줄 시나리오에 필요한가 + 구현 비용. 부분 수량은 환불 금액 분할, 상태 분화(부분반품중) 등 비용이 크지만 데모 시나리오에 없음.
- **선택**: (B). 클레임 신청 = OrderItem 하나가 통째로 대상.
- **트레이드오프**: 부분 수량 반품 불가. 시연에서 문제되지 않고, 필요해지면 OrderItem을 수량 1로 쪼개 담는 우회도 가능.

### D3. 결제 실패 시 주문을 남긴다 (PENDING → FAILED, 재시도 가능)

- **문제**: 모의 결제가 실패하면 주문 레코드를 지울지, 실패 상태로 남길지.
- **선택지**: (A) 실패 시 주문 미생성(결제 성공시에만 생성) (B) 주문 먼저 생성 → 결제 결과로 상태 전이
- **기준**: 기능 정의의 "결제 실패 시 안내 및 **재시도**" — 재시도하려면 실패한 주문 컨텍스트(상품, 배송지)가 남아 있어야 UX가 성립.
- **선택**: (B). `PENDING`(생성) → 모의 PG 결과에 따라 `PAID` 또는 `PAYMENT_FAILED`. 실패 주문에서 "다시 결제하기" 가능.
- **트레이드오프**: 영원히 PENDING/FAILED로 남는 쓰레기 주문 발생 → 데모 규모에선 무시. (선택적으로 24h 후 만료 배치 — 구현 안 해도 됨)

### D4. 배송은 스케줄러가 자동 전이하는 mock으로 구현한다

- **문제**: 실제 택배사 연동은 불가능하지만, 취소(배송 전)/반품·교환(배송완료 후)/후기(배송완료 후) 규칙이 전부 배송 상태에 의존한다.
- **선택**: 결제 완료 시 아이템 `ORDERED` → 스케줄러가 **5분 후 `SHIPPING`**, **다시 5분 후 `DELIVERED`** 로 자동 전이. 간격은 `app.mock-delivery.*` 설정값으로 조정 가능(데모 리허설 때 짧게 줄일 수 있게).
- **트레이드오프**: 실제 물류와 무관한 가짜 상태. 데모 목적상 충분하며, 시연 중 "방금 산 상품을 바로 반품"이 가능하도록 간격을 설정으로 뺐다.

### D5. 클레임은 관리자 페이지에서 승인/거절로 처리한다 (자동 완료 아님)

- **문제**: 반품 신청 후 "처리 상태 조회"를 보여주려면 누군가 상태를 진행시켜야 한다.
- **선택지**: (A) 스케줄러 자동 승인 (B) 관리자 페이지에서 수동 승인/거절
- **기준**: 관리자 페이지의 데모 가치. 문의/신고만으로는 관리자 화면이 얇은데, 클레임 처리가 있으면 "사용자 신청 → 관리자 처리 → 사용자가 상태 확인"의 풀 사이클을 시연할 수 있다. (2026-07-07 팀 결정)
- **선택**: (B). 승인 → 완료 상태(`CANCELLED`/`RETURNED`/`EXCHANGED`), 거절 → 신청 전 상태로 복귀(재신청 가능). 교환 승인은 상태만 `EXCHANGED`로 종결(재배송 사이클 없음 — 단순화).
- **트레이드오프**: 데모 중 관리자 계정 전환이 필요 — 시연 시나리오에 관리자 화면 컷을 넣어 오히려 어필 포인트로 활용.

### D7. 결제는 실 PG 테스트 모드 대신 자체 mock으로 구현한다

- **문제**: 모의 결제를 어떻게 구현할지 — 어차피 실결제는 안 되는데 실 PG(토스페이먼츠 등) 테스트 모드를 붙일지, 자체 mock으로 갈지.
- **선택지**: (A) 자체 mock (서버 내부에서 성공/실패 판정) (B) 실 PG 테스트 모드 연동 (위젯 + 승인 API)
- **기준**: ① 기능 정의가 "모의 결제 — 실제 PG 미연동"으로 명시 ② 결제는 이 서비스의 차별점이 아님(차별점은 에이전트) — 차별점 아닌 곳에 외부 의존(키 관리, 위젯 연동, 네트워크)을 들이면 시연 리스크만 늘어남.
- **선택**: (A). 실패 재현은 결제 수단의 "테스트: 결제 실패" 옵션으로(랜덤 실패는 데모를 망침).
- **트레이드오프**: 실제 결제 UX(인증창)의 리얼함 포기. 결제 판정을 `PaymentService` 인터페이스 뒤에 격리해, 고도화 때 토스페이먼츠 테스트 모드 구현체로 교체 가능하게 해서 최소화.

### D6. 상태는 이력 테이블 없이 현재 값만 저장한다

- **문제**: 상태 변경 이력(언제 SHIPPING이 됐나)을 별도 테이블로 남길지.
- **기준**: 소비처가 있는가 — 배송 타임라인 UI가 없고(주문 내역에 "상태 값 표시"만), 판매자 지표는 user_event 로그로 커버.
- **선택**: `OrderItem.status` 현재 값 + `status_changed_at` 타임스탬프 1개만. 이력 테이블 없음.
- **트레이드오프**: 과거 시점 추적 불가. 필요해지는 순간(타임라인 UI 추가 등) `order_item_status_history` 테이블을 추가하면 되고, 그 전까지는 YAGNI.

## 2. 상태 정의

### 2-1. Order.status (결제 수준)

| 상태 | 의미 | 진입 조건 |
|---|---|---|
| `PENDING` | 주문 생성됨, 결제 전 | 결제 화면에서 "결제하기" 요청 시 생성 |
| `PAID` | 모의 결제 성공 | mock PG 승인 |
| `PAYMENT_FAILED` | 모의 결제 실패 | mock PG 거절. 재시도 가능 |

- 모의 결제 실패 트리거: 결제 수단 선택지에 **"테스트: 결제 실패"** 옵션을 둔다(선택 시 무조건 실패). 그 외 수단은 무조건 성공. 이유: 실패 케이스를 시연자가 의도적으로 재현할 수 있어야 하고, 랜덤 실패는 데모를 망친다.
- `PAID` 이후 Order.status는 다시 변하지 않는다. 취소/반품에 의한 "전체 환불됨" 같은 파생 표현은 아이템 상태에서 계산한다(§4).

### 2-2. OrderItem.status (이행 + 클레임 수준)

```
                          (스케줄러 5분)        (스케줄러 5분)
   [결제 성공] ─▶ ORDERED ────────────▶ SHIPPING ────────────▶ DELIVERED
                    │                                            │
                    │ 취소 신청                                    │ 반품 신청          │ 교환 신청
                    ▼                                            ▼                  ▼
             CANCEL_REQUESTED                            RETURN_REQUESTED   EXCHANGE_REQUESTED
                    │ 관리자 승인                                  │ 관리자 승인         │ 관리자 승인
                    ▼                                            ▼                  ▼
                CANCELLED                                    RETURNED           EXCHANGED

   ※ 관리자 거절 시: CANCEL_REQUESTED → ORDERED, RETURN/EXCHANGE_REQUESTED → DELIVERED (신청 전 상태 복귀, 재신청 가능)
```

| 상태 | 의미 | 종결 상태? |
|---|---|---|
| `ORDERED` | 결제 완료, 배송 전 | ✕ |
| `SHIPPING` | 배송 중 | ✕ |
| `DELIVERED` | 배송 완료 | ✕ (클레임/후기의 출발점) |
| `CANCEL_REQUESTED` | 취소 신청 접수 | ✕ |
| `CANCELLED` | 취소 완료 | ✔ |
| `RETURN_REQUESTED` | 반품 신청 접수 | ✕ |
| `RETURNED` | 반품 완료 | ✔ |
| `EXCHANGE_REQUESTED` | 교환 신청 접수 | ✕ |
| `EXCHANGED` | 교환 완료 | ✔ |

### 2-3. 허용 전이 표 (이 표에 없는 전이는 전부 400)

| From | To | 트리거 |
|---|---|---|
| `ORDERED` | `SHIPPING` | 스케줄러 |
| `SHIPPING` | `DELIVERED` | 스케줄러 |
| `ORDERED` | `CANCEL_REQUESTED` | 사용자 취소 신청 |
| `DELIVERED` | `RETURN_REQUESTED` | 사용자 반품 신청 |
| `DELIVERED` | `EXCHANGE_REQUESTED` | 사용자 교환 신청 |
| `CANCEL_REQUESTED` | `CANCELLED` | 관리자 승인 |
| `RETURN_REQUESTED` | `RETURNED` | 관리자 승인 |
| `EXCHANGE_REQUESTED` | `EXCHANGED` | 관리자 승인 |
| `CANCEL_REQUESTED` | `ORDERED` | 관리자 거절 (신청 전 상태 복귀) |
| `RETURN_REQUESTED` | `DELIVERED` | 관리자 거절 |
| `EXCHANGE_REQUESTED` | `DELIVERED` | 관리자 거절 |

주의: `SHIPPING` 상태에서는 취소도 반품도 불가(배송 중 공백 구간). 의도된 규칙 — 실제 커머스와 동일하며, 데모에선 5분만 기다리면 DELIVERED가 된다.

## 3. 상태별 가능 액션 매트릭스 (서버가 검증해야 하는 규칙)

| OrderItem 상태 | 취소 신청 | 반품 신청 | 교환 신청 | 후기 작성 |
|---|---|---|---|---|
| `ORDERED` | ✔ | ✕ | ✕ | ✕ |
| `SHIPPING` | ✕ | ✕ | ✕ | ✕ |
| `DELIVERED` | ✕ | ✔ | ✔ | ✔ |
| `*_REQUESTED` | ✕ | ✕ | ✕ | ✕ |
| `CANCELLED` / `RETURNED` | ✕ | ✕ | ✕ | ✕ |
| `EXCHANGED` | ✕ | ✕ | ✕ | ✔ |

- 후기 작성 조건 = `DELIVERED` 또는 `EXCHANGED` + **해당 OrderItem으로 작성한 후기가 아직 없음** (아이템당 후기 1개).
- `EXCHANGED`에서 후기 허용 이유: 교환 완료 = 상품을 최종 수령한 상태이므로.
- 이 매트릭스는 프론트 버튼 노출 규칙이자 백엔드 검증 규칙이다. **프론트가 숨겨도 백엔드는 반드시 재검증한다** (LLM 콜백 등 다른 경로로 같은 API가 호출되기 때문).

## 4. 주문 대표 상태 (표시용 파생값)

주문 목록에서 "주문 건별 상태 값"을 한 줄로 보여줘야 한다. **DB에 저장하지 않고** 아이템 상태에서 계산한다(파생값 저장 금지 원칙).

규칙 (위에서부터 첫 매칭):
1. `Order.status == PENDING` → "결제 대기"
2. `Order.status == PAYMENT_FAILED` → "결제 실패"
3. 아이템 중 `*_REQUESTED` 존재 → "취소/반품/교환 처리중"
4. 아이템 전부 종결(`CANCELLED`/`RETURNED`/`EXCHANGED`) → "처리 완료"
5. 아이템 중 `ORDERED` 존재 → "배송 준비중"
6. 아이템 중 `SHIPPING` 존재 → "배송중"
7. 그 외(전부 `DELIVERED` 또는 종결 혼합) → "배송 완료"

문의 챗봇의 주문 상태 콜백도 이 파생 규칙의 결과 + 아이템별 상태 목록을 함께 반환한다(LLM이 "키보드는 배송중이고 마우스는 반품 처리중이에요"라고 답할 수 있게).

## 5. 클레임 신청 데이터

클레임은 상태 전이만으로는 부족하다 — "취소·반품·교환 내역" 화면이 신청 건 목록을 요구하므로 신청 레코드가 필요하다.

`claim` 테이블 (상세 스키마는 02 데이터 모델 문서):
- `type`: `CANCEL` / `RETURN` / `EXCHANGE`
- `status`: `REQUESTED` / `COMPLETED` / `REJECTED` — OrderItem.status와 항상 같은 트랜잭션에서 동기 전이. 거절 시 아이템은 신청 전 상태로 복귀
- `reason`: 신청 사유 텍스트 (선택 입력), `reject_reason`: 거절 사유 (거절 시 필수)
- `processed_by` / `processed_at`: 처리한 관리자 id와 시각
- `order_item_id`: 대상 아이템. 아이템당 `REQUESTED` 상태 클레임 최대 1개 — 거절 건은 재신청 가능해야 하므로 DB unique가 아니라 서비스 레이어에서 검증

환불 금액 = 해당 OrderItem의 (스냅샷 가격 × 수량). 모의 결제라 실제 환불 처리는 없고 표시용.

## 6. 스케줄러 명세

| 잡 | 주기 | 동작 |
|---|---|---|
| 배송 전이 | 1분마다 | `ORDERED` 중 `status_changed_at`이 5분 경과 → `SHIPPING`. `SHIPPING` 중 5분 경과 → `DELIVERED` |

- 클레임 전이는 스케줄러가 아니라 관리자 승인/거절 API로만 일어난다(D5).
- 간격은 `application.yml`의 `app.mock.shipping-minutes`, `app.mock.delivery-minutes`로 설정. 기본 5/5분.
- 구현: Spring `@Scheduled` + 단순 UPDATE 쿼리. 인스턴스 1대 전제(분산 락 불필요 — 데모 규모 결정).
