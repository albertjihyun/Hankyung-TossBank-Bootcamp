# 설계 의사결정 기록 (ADR)

살래말래 프로젝트의 주요 설계 결정과 그 근거를 기록한 문서다. 각 결정은 네 가지를 함께 남긴다.

1. **우리가 선택한 안** — 무엇을 결정했는가
2. **검토했지만 채택하지 않은 대안** — 무엇과 비교했는가
3. **선택 기준** — 어떤 가치를 더 무겁게 봤는가
4. **트레이드오프** — 무엇을 얻고 무엇을 포기했는가

코드 곳곳의 주석에서 `ADR-XXX` 형태로 이 문서를 참조한다.

## 일관되게 따른 판단 기준

1. **"왜"가 "무엇"보다 먼저** — 기능을 정의하기 전에 사용자 가치와 문제를 정의한다.
2. **읽기 빈도 ≫ 쓰기 빈도 → 쓰기 시점 비용을 받아들인다** — 반정규화/트랜잭션 통합 결정의 근간.
3. **파생 가능한 값은 어디에도 저장하지 않는다** — DB에도, 응답에도. 원시 데이터에서 계산한다.
4. **다층 방어선(Defense in Depth)** — 하나의 정합성 보장 메커니즘에만 의존하지 않는다. 트랜잭션, CHECK, UNIQUE는 서로 다른 책임.
5. **관심사 분리** — 동기 요청 처리와 비동기 시간 트리거는 다른 프로세스. 데이터는 서버, 표현은 프론트엔드.
6. **2주 MVP 범위 존중** — 기술적 욕심보다 완성과 발표 가능한 수준을 우선. "Won't Have"를 명시적으로 정의.

## ADR-001. 아키텍처: 풀스택 통합과 워커 분리 — 라이프사이클 기준의 두 결정

아키텍처는 표면적으로 하나의 구조처럼 보이지만, 실제로는 서로 다른 기준으로 따로 내린 **두 개의 독립된 결정**이다.

- **결정 A — 사용자 요청 처리: Next.js 풀스택 통합.** 페이지 렌더링과 API 서버를 하나의 Next.js 프로세스로 통합한다. 백엔드를 별도 분리하지 않는다.
- **결정 B — 시간 트리거: systemd timer.** 알림 스케줄러는 systemd timer가 매 정각 oneshot으로 Node.js 스크립트를 깨워 1회 실행하고 종료한다. 상주 워커 프로세스를 두지 않는다.

두 결정을 정리하며 발견한 공통 원칙:

> **분리는 의지의 표현이다. 분리할 이유가 진짜 있을 때만 분리한다.**

- 결정 A: 사용자 요청 처리에서는 분리할 이유가 없다 → 통합
- 결정 B: 시간 트리거는 라이프사이클이 달라 분리할 이유가 있다 → 분리 (분리의 표현 방식은 OS 표준인 systemd timer)

같은 원칙이 반대 결과로 적용된 두 사례다.

### 결정 A. Next.js 풀스택 통합

**선택지**

- (A) Next.js(페이지) + Express 등 별도 백엔드 — 분리 구조
- (B) Next.js 풀스택 (페이지 + API Routes 통합) — 채택

**선택 기준**

- 백엔드 분리의 진짜 가치는 HTTP 경계를 통해 두 시스템이 서로를 모른 채 작동한다는 데 있다 — 언어 자유도, 독립 배포, 팀 분업. 이 경계를 지킬 의지가 없다면 분리는 형식만 남고 비용만 늘어난다.
- 도메인 규모: REST 단일 도메인. Express의 미들웨어 자유도가 실제로 쓸 데가 없는 자유도.
- 2주 4명 일정: 두 프레임워크를 깊이 다루는 비용보다 하나에 집중하는 게 합리적.

**채택 이유** — 분리해도 결국 같은 레포·같은 머신·같은 팀에 둘 것이었다. HTTP 경계를 유지할 의지가 없다는 뜻이고, 분리는 형식만 남는다. 반면 통합의 이점은 실제로 회수됐다. 특히 서버 컴포넌트에서 DB 직접 조회가 가능해서, 카테고리 같은 마스터 데이터와 대시보드·공유 페이지는 API 라우트를 만들지 않았다.

**트레이드오프**

- 장점: 서버 컴포넌트의 DB 직접 조회로 API 라우트 자체를 줄임, 단일 배포 단위(CORS·환경변수 두 세트 회피), 인증 미들웨어가 한 프로세스 안에서 단순.
- 단점: 백엔드 자유도가 Next.js 컨벤션 안으로 제한됨. App Router는 비교적 새로운 패러다임이라 트러블슈팅 참고 사례가 제한적. 서버/클라이언트 컴포넌트 구분이 인지 비용을 만듦.

**설계 초반의 사고와 교정** — 초반에는 "cron 워커로 Node 프로세스를 하나 띄울 거면, 거기에 백엔드 API까지 함께 두면 되지 않나"라는 통합 방향의 사고를 했다. 공부하면서 교정한 것: node-cron은 그냥 npm 패키지이고 어떤 Node 프로세스에든 쓸 수 있다. 분리 기준은 "같은 패키지를 쓸 수 있느냐"가 아니라 **라이프사이클이 같으냐**다. 백엔드 API와 cron을 한 프로세스에 합치면 한쪽의 사고가 다른 쪽을 끌고 죽는 운명 공동체가 된다. 이 교정을 거쳐 두 결정을 분리해서 보게 됐다.

### 결정 B. 시간 트리거: systemd timer (1차 결정은 별도 Node.js 워커, 이후 갱신)

**선택지**

- (A) Next.js 단일 프로세스에 node-cron 등록
- (B) Next.js + 별도 Node.js 워커 (node-cron 상주) — 1차 결정이었으나 (C)로 갱신
- (C) Next.js + systemd timer + oneshot 스크립트 — 채택
- (D) Next.js + GCP Cloud Scheduler → 웹훅

**선택 기준** — 서비스 안정성 / DB 정합성·동시성 / 기능 구현 충분성 / 자원 관리·보안 네 가지 가치로 평가. 앞의 셋은 (B)(C)(D) 모두 무승부였고, 자원 관리·보안 축과 개발 난이도가 결정을 갈랐다.

**채택 이유**

- (A): Next.js의 요청 기반 라이프사이클과 충돌. 핸들러 로드 시점이 보장되지 않고, 인스턴스 두 개면 중복 발송. 일찍 배제.
- (B): 1차 결정. 시간 정책이 git 레포 안에 있다는 장점이 있으나, 시간 트리거라는 본질에 비해 24시간 상주 프로세스를 살려두는 것이 한 단계 우회.
- (D): 가장 안정적이지만 GCP IAM·OIDC·Cloud Logging 등 새로 학습할 개념이 많고, 공개 엔드포인트를 노출해야 하며, 디버깅 지점이 세 곳으로 흩어짐. 우리 도메인은 놓친 정각의 알림이 가치 없는 정책이라 "VM 외부 시계"의 핵심 가치가 실효로 이어지지 않음.
- (C): 시간 트리거의 책임을 OS에 위임. 상주 프로세스 없음(상시 메모리 점유 0, 상시 공격 표면 0). 학습 부담은 unit 파일 문법 정도. 디버깅이 `journalctl` 한 곳에 모임.

**트레이드오프**

- 장점: 자원 사용 패턴이 "간헐적 작업"이라는 본질과 일치. 매 실행이 fresh 프로세스라 메모리 누수가 원리적으로 없음. OS 표준 도구 활용(PM2 등 불필요). 워커 코드를 바꿔도 다음 정각에 새 코드가 자동 반영.
- 단점과 회피책:
  - 시간 정책(`OnCalendar`)이 unit 파일에 위치 → unit 파일을 레포 `deploy/`에 두고 `install.sh`로 시스템 디렉토리에 복사. 진실은 레포에, 동기화는 배포 스크립트로.
  - 로컬에서 트리거 메커니즘 재현 불가(systemd는 리눅스 전용) → 발송 로직을 `lib/notifier.js`에 모으고 로컬에선 `scripts/dev-notify.js`로 같은 함수를 직접 호출.
  - systemd timer 기본 정확도(±60초) → `AccuracySec=1s` + 코드 측 `floorToHour()`로 정각 격자에 재정렬.
  - VM 자체가 단일 장애점 → 놓친 정각의 알림은 가치 없는 정책이라 `Persistent=false`로 명시적 결정.

**(B)에서 (C)로 갱신한 과정과 정직한 평가** — GCP 배포를 준비하며 systemd를 공부하다가 timer 기능을 발견했고, 별도 워커 프로세스 자체가 필요한지 재검토했다. 검토 중 node-cron의 단점(DB 풀 재사용 손실, lib 재로딩 비용, 상주 메모리)을 부풀려 짚는 흐름이 있었는데, 백지에서 다시 보니 매 정각 1회 실행되는 가벼운 작업에서는 전부 실효 없는 단점이었다. 부풀린 명분을 걷어내고도 살아남은 (C)의 근거는 세 가지다: (1) 본질 일관 — 간헐적 작업에 간헐적 자원 사용, (2) 공격 표면 최소화, (3) OS가 이미 잘하는 일에 위임. 원칙을 뒤집은 게 아니라 끝까지 적용한 결과다.

**시간 트리거 작동 방식** — 트리거는 회원별로 등록하지 않는다. timer는 매 정각에 깨어나는 작업 딱 하나만 존재하고, "지금 정각에 알림 보낼 사람이 누구인가"는 DB에 묻는다. 스케줄링 정보의 진실은 `items.expire_at` 컬럼에 있고, timer는 시간 진행 트리거만 담당한다. 이 패턴이 성립하려면 expire_at을 정각 단위로 저장하는 결정이 필수다 — 사용자 선택 단위, timer 주기, DB 저장 단위가 같은 격자에 맞아야 SQL 한 줄로 매칭이 끝난다.

**운영 계층** — GCP VM에서 systemd가 관리하는 unit: `sallae-web.service`(Next.js 상주), `sallae-notifier.timer` + `sallae-notifier.service`(매 정각 oneshot), cloudflared(외부 터널). unit 파일은 레포 `deploy/`에 있고 `install.sh`가 복사·활성화한다.

## ADR-002. 쓰기 시점 갱신 전략: 반정규화와 계산값 캐시

**결정** — 3NF를 기본으로 하되, 읽기 빈도가 쓰기 빈도를 압도하는 두 데이터에 한해 쓰기 시점에 미리 계산해 저장한다. 갱신은 결정(decision) 이벤트의 트랜잭션 내에서 동기 수행한다.

| 대상 | 종류 | 원리 |
|---|---|---|
| `user_monthly_stats` 월별 집계 테이블 | 반정규화 | items GROUP BY로 계산 가능한 집계값을 미리 저장 — JOIN/GROUP BY 회피 |
| `users.level` 컬럼 | 계산값 캐시 | `calculateLevel()` 함수 결과를 컬럼에 미리 저장 — 함수 호출 회피 |

**대안** — (A) 완전 정규화·매번 실시간 계산: 데이터 누적 시 items 풀스캔 + GROUP BY 부담. (C) 배치 비동기 갱신: 결정 직후 반영이 지연되어 "방금 아꼈는데 왜 안 보여?"로 UX가 깨짐.

**트레이드오프** — 대시보드 응답이 빨라지고 결정 직후 즉시 반영되는 대신, 결정 트랜잭션이 무거워지고 정합성 리스크가 생긴다. 리스크는 트랜잭션 + CHECK 제약으로 방어한다(ADR-003, 004).

**용어 구분** — 반정규화는 다른 테이블의 데이터를 중복 저장(JOIN 회피), 계산값 캐시는 함수 계산 결과를 미리 저장(계산 회피). `users.level`은 levels 테이블이 없으므로(ADR-014) 엄밀히는 반정규화가 아니라 계산값 캐시다.

## ADR-003. 결정 트랜잭션 통합 처리

**결정** — `PATCH /api/items/:id/status` 한 번의 호출 안에서 다음 세 작업을 하나의 트랜잭션으로 묶는다. 중간 실패 시 전체 롤백.

1. `items.status`, `items.decided_at` UPDATE
2. `user_monthly_stats` UPSERT (year/month는 decided_at 기준)
3. `users.level` 재계산 후 UPDATE

**대안** — 통계·레벨을 별도 API나 비동기 잡으로 갱신하면 중간 상태가 노출되고 실패 복구가 복잡해진다.

**트레이드오프** — 강한 정합성과 응답 일관성을 얻는 대신 트랜잭션 길이와 락 범위가 늘어난다. 완화: 모든 쿼리가 PK 또는 UNIQUE 키 단일 행 대상이라 락 범위가 최소이고, 결정 빈도가 낮아(사용자당 하루 1~2회) 실질 충돌 가능성이 낮다.

**동시성 처리 세 계층** — 결정 API는 세 종류의 동시성 문제를 각기 다른 메커니즘으로 처리한다.

1. 동시 요청(멀티 디바이스 등) → `SELECT ... FOR UPDATE` 행 락으로 직렬화
2. 트랜잭션 중간 실패 → 자동 ROLLBACK으로 원자성 보장
3. 응답 손실 후 재시도 → 상태 기반 멱등 로직으로 200 응답 (ADR-007)

락은 동시성, 트랜잭션은 원자성, 멱등 로직은 UX. 각자 다른 책임이다.

## ADR-004. 정합성 보장: 다층 방어선

**결정** — 도메인 정합성을 트랜잭션(원자성) + CHECK 제약(애플리케이션 버그 방어) + UNIQUE 제약(동시성 방어) 세 레이어로 보장한다.

| 레이어 | 적용 위치 | 막는 문제 |
|---|---|---|
| 트랜잭션 | 결정 처리 (items + stats + level) | 중간 실패로 인한 부분 적용 |
| CHECK | `items`의 (status='waiting' ↔ decided_at IS NULL) | 코드 버그로 status만 바꾸고 decided_at 누락 |
| UNIQUE | `email_logs(item_id, type)` | 스케줄러 중복 실행으로 같은 알림 중복 발송 |
| UNIQUE | `users.email`, `users.share_token`, `categories.name` | 비즈니스 유일성 위반 |

트랜잭션은 "의도된 로직"을 묶어주지만 "애플리케이션 버그"는 막지 못한다. 한 레이어가 깨져도 다른 레이어가 막는다. 비용은 제약 위반 시 사용자 친화적 에러 메시지로 변환하는 추가 코드(예: `ER_DUP_ENTRY` → 이미 발송됨 처리).

## ADR-005. 인증: JWT (AT 15분 + RT 7일) + Refresh Token Rotation

**결정**

- Access Token(15분) + Refresh Token(7일) 듀얼 토큰
- RT는 bcrypt 해시로 `users.refresh_token`에 저장
- 사용 시마다 새 토큰 발급 + 기존 무효화 (Rotation)
- 이미 사용된 RT 재사용 감지 시 `token_version` 증가로 전체 세션 강제 만료
- AT/RT 모두 HttpOnly + SameSite=Strict 쿠키

**대안** — 세션 기반 인증은 세션 저장소(Redis 등)가 필요하고 웹/워커 두 프로세스가 같은 저장소를 봐야 해서 MVP 범위 초과. JWT 단일 토큰은 길게 두면 탈취 피해가 크고 짧게 두면 UX가 나빠짐.

**보안 범위 원칙** — "팀이 학습한 범위 안에서 견고하게 구현하고 설명 가능한 제어"를 우선한다. HttpOnly(XSS 방어) + SameSite=Strict(CSRF 방어) 적용. AT를 HttpOnly 쿠키로 전환하면서 CSRF 노출면이 생겼고, 이해하고 학습한 뒤 SameSite=Strict를 함께 적용했다.

**인증 계층 방어선**

- 1차: 미들웨어 — accessToken 쿠키를 `jose`(Edge Runtime 호환)로 서명 검증. 보호 경로 미인증 접근 시 로그인 리다이렉트.
- 2차: API 내부 `getSessionUser` — `jsonwebtoken`으로 재검증 + 소유권 확인.

**트레이드오프** — 무상태, 두 프로세스 간 세션 공유 불필요, 탈취 대응 견고. 대신 RT Rotation은 동시 요청 경합 처리가 필요하다.

---

## ADR-006. 알림 정책: 24시간 경계값 처리

**결정** — `before_24h` 알림은 다음을 모두 만족할 때만 발송한다: `status='waiting'`, `expire_at - INTERVAL 24 HOUR = 현재 정각`, `expire_at - INTERVAL 24 HOUR > created_at + INTERVAL 1 HOUR`.

**이유** — 등록 직후 "24시간 후 만료입니다" 알림은 사용자가 등록 사실을 기억하는 시점에 도달해 무의미하거나 짜증을 유발한다. 24시간 이하 단기 쿨링오프는 조건이 자연스럽게 매칭되지 않아 expire 알림 1회만 발송된다. N=1시간은 등록 최소 제약("현재 시각 기준 최소 1시간 이후")과 일관된 가설값으로, 추후 지표로 보정할 영역이다.

## ADR-007. 멱등성: 상태 기반 멱등 처리

**결정** — `PATCH /api/items/:id/status`는 멱등하게 동작한다. 요청 status가 현재 status와 동일하면 변경 없이 200. 다른 결정 상태로의 전환 시도는 409 Conflict.

**대안** — 멱등성 처리 없음(더블클릭·응답 손실 시 사용자가 에러를 봄 — UX 결함), Idempotency-Key 헤더(키 저장소 + 만료 정책 필요 — MVP 범위 초과).

**전체 경우의 수**

| 상황 | DB status | 요청 status | 응답 |
|---|---|---|---|
| 정상 결정 | waiting | passed / bought | 200, 트랜잭션 실행 |
| 트랜잭션 실패 뒤 재시도 | waiting (롤백됨) | 같은 결정 | 200, 첫 시도처럼 처리 |
| 응답 손실 후 재시도 | passed (커밋됨) | passed | 200, 변경 없음 |
| 결정 후 마음 바뀜 | passed | bought | 409 Conflict |
| waiting으로 되돌림 | passed / bought | waiting | 400 Bad Request |

**부수 설계** — 정상 경로에서는 프론트가 확인 모달과 버튼 비활성화로 비정상 요청을 막는다. 서버 멱등 처리는 멀티 디바이스, 개발자 도구 직접 호출, 클라이언트 버그 등 비정상 경로의 방어다.

---

## ADR-008. 목록 조회: 페이지네이션과 필터 설계

**결정** — 상태 필터는 쿼리 파라미터(`?status=...`), 페이지네이션은 offset 기반(`?page=1&limit=20`).

**이유** — 상태 필터는 같은 리소스의 부분집합이므로 별도 엔드포인트가 아닌 쿼리 파라미터가 맞다. 페이지네이션은 cursor 기반을 먼저 검토했으나, 사용자당 항목 수가 수백 단위를 넘기 어려운 도메인이라 cursor가 빛나는 "깊은 페이지·큰 데이터셋" 조건이 성립하지 않는다. 익숙하고 디버깅 쉬운 offset을 선택하고, 전체 페이지 수 표시가 가능하다는 부가 이점도 얻었다. 항목 수가 수천 단위로 폭증하면 cursor 전환을 검토한다.

**인덱스** — `idx_items_user_status_expire (user_id, status, expire_at, id)`가 사용자별 + 상태 필터 + 만료일 정렬 + tiebreaker를 한 인덱스로 커버한다.

## ADR-009. 공유 URL: share_token 기반 단순 rotation

**결정** — 토큰 발급 시 기존 토큰 즉시 무효화(덮어쓰기). `GET /api/share/:shareToken`은 인증 불필요, 무효 토큰은 404. 만료 토큰은 보관하지 않는다.

**대안** — userId를 URL에 직접 노출하면 순차 정수라 다른 사용자 페이지를 추측할 수 있다. 만료 토큰 별도 보관은 관리 비용이 MVP 범위를 초과하고, rotation의 의도("이전 링크를 더 이상 노출하고 싶지 않다")와도 어긋난다.

**트레이드오프** — 보안 모델과 구현이 단순해지는 대신, 이미 뿌린 공유 링크는 갱신 후 깨진다. "이 공유 링크는 더 이상 유효하지 않습니다" 안내 화면으로 보완한다.

## ADR-010. D-day 표현: days_left 백엔드 계산 (갱신됨)

**현재 결정** — 서버가 `expire_at`과 함께 `days_left`(`GREATEST(0, FLOOR(TIMESTAMPDIFF(SECOND, NOW(), expire_at) / 86400))`), `time_left_label`(D-day 또는 D-숫자)을 계산해 반환한다. 프론트엔드는 표시만 한다.

**원래 결정 (Superseded)** — 서버는 expire_at만 내려보내고 D-day 계산은 프론트엔드 책임("파생값은 저장하지 않는다" 원칙의 응답 스키마 적용).

**갱신 이유** — 프론트 계산은 클라이언트 기기 시간 기준이라 서버 시간과 어긋날 수 있고, 쿨링오프 앱에서 D-day는 사용자 의사결정에 직접 영향을 주는 값이다. 계산 책임을 백엔드로 일원화했다. 원칙(파생값 미저장)은 유지된다 — DB에 저장하지 않고 조회 시점에 SQL로 계산한다.

## ADR-011. 대시보드 만료 항목: 카운트만 표시

**결정** — 대시보드 상단 만료 알림 박스는 만료된 미결정 항목 개수만 표시하고, 클릭 시 위시리스트로 이동한다.

**이유** — 위시리스트가 항목 조회·결정의 단일 화면, 대시보드는 요약·알림. 대시보드에 항목 카드·결정 버튼을 다시 만들면 UI 이중 구현에 캐시 무효화도 두 곳이 된다. "알림은 대시보드, 관리는 위시리스트"로 역할을 분리했다. 만료 0개일 때는 박스 자체를 숨긴다.

---

## ADR-012. 위시리스트 정렬: 만료 미결정 우선, 결정 탭은 결정 시각순

**결정**

- 전체/대기중 탭: 만료 미결정 → 진행 중 → 결정됨 순. 각 그룹 내 `expire_at ASC`.
- 구매함/아낌 탭: `decided_at DESC` (최근 결정 순).
- 그룹 시각화는 섹션 헤더 없이 카드 뱃지 색상으로 구분.

**이유** — 대시보드의 "만료 N개 알림 → 위시리스트 이동" 동선에서 만료 미결정이 맨 위에 보여야 한다. 대기 항목은 만료일이 행동 우선순위라 자연스러운 정렬 기준이고, 결정된 항목은 결정 시각이 회고 순서로 더 의미 있는 시간축이다. 그룹의 도메인 의미에 맞춰 정렬 기준을 다르게 적용했다.

```sql
-- 전체 / 대기중 탭
ORDER BY
  CASE
    WHEN status='waiting' AND expire_at < NOW() THEN 0  -- 만료 미결정
    WHEN status='waiting' THEN 1                        -- 진행 중
    ELSE 2                                              -- 결정됨
  END ASC,
  expire_at ASC, id ASC

-- 구매함 / 아낌 탭
ORDER BY decided_at DESC, id DESC
```

## ADR-013. 결정된 항목의 카드 뱃지: 종류별 분리 표시

**결정** — `bought` → 구매함(회색, 중립), `passed` → 아낌(초록, 성취). 탭 라벨과 동일한 어휘.

**이유** — 탭이 이미 "구매함/아낌"으로 분리되어 있으므로 카드 뱃지도 같은 어휘가 멘탈 모델에 일관된다. "완료" 하나로 통합하면 전체 탭에서 두 결정이 시각적으로 구분되지 않는다. 구매함과 아낌은 도메인적으로 다른 결과(소비 vs 성취)라 색상으로도 분리했다.

## ADR-014. levels 테이블 제거: 정적 메타데이터는 코드 상수로

**결정** — `levels` 테이블을 DB 스키마에서 완전히 제거한다. 레벨 메타데이터(이름, 뱃지 경로)와 산정 기준 모두 `/lib/level.js`의 `LEVEL_THRESHOLDS` 상수 한 곳에서 관리한다. `users.level`(TINYINT UNSIGNED)은 FK 제약 없는 분류값 컬럼으로 유지한다.

**선택지** — (A) 이름·뱃지만 DB 테이블에(1차 결정), (B) 전부 코드 상수(채택), (C) 산정 기준까지 전부 DB에.

**이유** — 레벨은 5개 고정이고 사용자가 추가·삭제할 수 없는 완전한 정적 메타데이터다. DB 테이블을 두면 "레벨이 5개"라는 사실이 DB와 코드 두 곳에 존재해 어긋날 리스크가 생긴다. 코드 상수 한 곳이 단일 진실 원천이면 매칭 검증 로직 자체가 불필요하다. 레벨 명칭·뱃지 변경은 어차피 프론트 코드와 함께 PR로 반영되는 흐름이라 코드 관리가 자연스럽다.

**calculateLevel: 두 임계값 AND 조건** — `threshold_count`와 `threshold_amount`를 모두 넘긴 가장 높은 레벨을 반환한다. OR 조건이면 고가 항목 하나를 아껴 최고 레벨이 되는 부자연스러운 레벨업이 발생한다. 꾸준한 절약 습관 형성이라는 서비스 가치에 맞춰 두 조건을 모두 요구했다. 레벨업이 조금 어려워지는 대신 레벨 숫자가 의미를 갖는다.

**컬럼 설계 세부** — 컬럼명은 `level_id`가 아닌 `level`(`_id` 접미사는 다른 테이블 행 참조라는 관행적 신호인데 levels 테이블이 없으므로 잘못된 신호). 타입은 TINYINT UNSIGNED(5개 레벨에 INT는 과함). DEFAULT 1(신규 가입 = 충동 새싹).

**트레이드오프** — 단일 진실 원천, 스키마 단순화를 얻는 대신, DB만 봐서는 level 값의 의미가 안 보인다 → 컬럼 주석으로 "코드 상수와 매핑"을 명시했다.

## 결정들 사이의 관계

```
ADR-001 (아키텍처 — 풀스택 통합 + 시간 트리거 분리)
   ├─ 결정 A (Next.js 풀스택 통합)
   │    └─ 서버 컴포넌트 DB 직접 조회로 카테고리·대시보드·공유 API 라우트 제거
   └─ 결정 B (systemd timer)
        ├─ ADR-005 (JWT 무상태 인증이 이 분리를 자연스럽게 함)
        └─ ADR-006 (timer가 깨우는 oneshot 스크립트가 알림 정책을 실행)

ADR-002 (쓰기 시점 갱신 전략)
   ├─ ADR-003 (결정 트랜잭션이 갱신 데이터를 동기 처리)
   └─ ADR-004 (다층 방어선이 정합성 리스크를 막음)

ADR-003 (결정 트랜잭션)
   └─ ADR-007 (멱등 처리 — 결정 API의 응답 손실 시나리오)

ADR-008 (목록 조회)
   └─ ADR-012 (정렬 구문이 인덱스를 활용)

ADR-011 (대시보드 만료 알림)
   └─ ADR-012 (위시리스트 정렬이 대시보드 → 위시리스트 동선을 받침)

ADR-014 (levels 테이블 제거)
   └─ ADR-002 (users.level이 "반정규화"가 아닌 "계산값 캐시"로 분류되는 근거)
```

## 작성 규칙

1. 결정 하나에 ADR 하나. 너무 큰 결정이면 쪼갠다.
2. 항상 "검토했지만 채택하지 않은 대안"을 함께 적는다.
3. 선택 기준을 명시하고, 다른 ADR과 일관되는지 확인한다.
4. 트레이드오프를 솔직하게 적는다. "단점 없음"인 ADR은 아직 충분히 생각하지 않은 것이다.
5. 결정 변경 시 새 ADR로 덮어쓰지 않고 "Superseded" 메모를 남긴다.
6. 대안이 사실상 없는 것(업계 상식)이나 주석으로 충분한 것은 ADR로 만들지 않는다.
